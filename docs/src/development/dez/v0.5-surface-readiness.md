# Dez v0.5 surface readiness

This is the active source-readiness plan for Dez v0.5. It builds on the
0.4.0 source candidate and its exact-artifact evidence without claiming that a
v0.5 package exists, passes runtime validation, or is ready for promotion.
[Fork Notes](./fork-notes.md) remain the permanent product and architecture
authority. The [Native Surface Contract](./surface-contract.md) remains the
authoritative interaction and ownership specification.

## Release promise

> Open a Workspace, start or resume terminal-native work, supervise only what
> needs attention, use the complete native editor toolset, and return after a
> restart without reconstructing context.

The primary loop is one native journey:

```text
Open Workspace
-> start or resume work in a native tab
-> supervise bounded Activity in Workspaces
-> inspect Files, Search, Diagnostics, Debug, Git, and diffs
-> review and continue with Workspace and process ownership intact
```

Dez v0.5 is a complete Workspace-first development environment with a sharp
terminal-agent supervision wedge. It is not a terminal dashboard, chat shell,
custom tab implementation, multiplexer clone, or visual wrapper around Zed.

## v0.5 product boundary

The hierarchy is fixed:

> **Workspace is identity. Pane is target. Tab is content. Activity is signal.**

| Surface | v0.5 job | Native owner | Release requirement |
| --- | --- | --- | --- |
| Home | start or resume the product loop | closeable Main Work Area tab | one primary Workspace action; state-aware tool launch; no overlay |
| Workspaces | switch codebases and supervise current work | `MultiWorkspace`, `Workspace`, and owning stores | bounded Activity, activation-only Layout, truthful recovery, no duplicate tab state |
| Main Work Area | own editing, tools, terminals, review, and splits | native pane and tab model | selected tab, adjacent `+`, Back/Forward, overflow, split, drag, close, preview, and focus remain native |
| Status bar | preserve durable context and the Workspaces recovery route | native status items | one line; responsive identity; no transient prose |
| Terminal | render shells, agents, tasks, tmux, and Herdr | `TerminalView` and terminal host | TUI remains authoritative; ownership and failure stay inline |
| cmux | continue in the external Workspace owner | cmux | explicit handoff; no simulated cmux UI or fake attach |
| Files, Search, Git, Diagnostics, Debug | complete the development loop | existing Zed surfaces | ordinary pane tabs with honest loading, empty, failure, and recovery states |
| Settings | expose only working product choices | native Settings store and renderers | Workspace and terminal choices first; no dead rows or internal diagnostics |

## Primary user stories

### Start and focus

1. Open or restore one Workspace.
2. Start the configured terminal, Codex, Claude Code, OpenCode, a native shell,
   or Workspace tmux from Home or the adjacent native `+`.
3. Keep the new destination in the current pane unless the user explicitly
   splits.
4. Show the active Workspace, focused pane, selected tab, and durable status
   without a second toolbar.

### Supervise and return

1. Project only active, running, actionable, recoverable, or review-ready work
   into Activity.
2. Keep idle open content in Layout and completed history in Agent History.
3. Select an Activity or Layout row to focus its existing owner.
4. Preserve the current Main Work Area while browsing or searching Workspaces.

### Inspect and verify

1. Open Files, Search, Diagnostics, Debug, Git, or Review as ordinary tabs.
2. Keep every file and tool reachable after another item opens.
3. Keep errors and recovery inside the owning surface with the failed content
   or terminal output still visible.
4. Never claim a successful check, live process, migration, or ownership
   transfer without authoritative evidence.

## Adaptive Workspace starts

Dez may adapt the first useful destination, but it never invents a permanent
mode, opens an unexplained split, or replaces restored user state. The startup
policy is:

1. A valid restored Workspace layout always wins.
2. An explicit **Workspace Layout** action always wins for the current
   Workspace.
3. A user-selected startup intent may choose the first native tab when a
   Workspace has no restorable layout.
4. Without an explicit preference, Dez opens **Focus Work Area** and keeps
   Files, Git, Debug, and the Built-in Agent available from the adjacent `+`,
   command palette, and Workspace Layout menu.
5. Only **Split Work Area** may create multiple populated work areas, and only
   after an explicit user action.

The source setting is **New Workspace Starts With** (`startup_intent`). It is
consulted only after root resolution and explicit-item opening, so it cannot
replace a requested file, resurrect a tool over a restored layout, or turn an
empty Home window into a phantom Workspace. Native panel initialization owns
the destination registry; in particular, the Built-in Agent owner is loaded
without creating a terminal or starting an Agent Session.

The supported intents are small and map to existing native owners:

| Intent | First destination | Optional explicit recipe | What it never does |
| --- | --- | --- | --- |
| Direct | last file or Files | Work Area + Files | open a terminal or split automatically |
| Agentic | configured terminal or Home launcher | Work Area + Built-in Agent | wrap a terminal TUI in chat or promote Activity into the work area |
| Review | Git Changes or Review Changes | Work Area + Git | stage, discard, commit, or claim checks automatically |
| Debug | Debug setup | Work Area + Debug | start a build, adapter, or debug session automatically |
| Focus | Home or empty Main Work Area | Focus Work Area | open a second pane |

These are startup intents, not Studio/Projects modes. They do not add a mode
switcher, duplicate pane state, or change the universal Workspace → pane → tab
hierarchy. The setting must be reversible, Workspace-scoped when appropriate,
and visible in the native Settings file even if its graphical control is
deferred.

Debug startup opens the already-loaded native Debug panel through the Workspace
debugger provider. It does not synthesize a dock item, dispatch the Debug start
action, or create a session; the user still owns configuration and launch.

## Upstream integration lane

The incorporated Zed baseline remains `b0f145f4aec671970340a528cb8197181e969e8c`.
On 2026-08-06, the observed official `main` target was
[`b914ba5cb3f4619450ad0de38adbb6b215752b74`](https://github.com/zed-industries/zed/commit/b914ba5cb3f4619450ad0de38adbb6b215752b74)
and the latest published release was
[`v1.14.2`](https://github.com/zed-industries/zed/releases/tag/v1.14.2). These
references are planning evidence only; neither has been merged into the current
Dez source candidate.

### Current merge inventory

The upstream tracking ref was refreshed to that exact `main` target without
merging it. Relative to the incorporated baseline, upstream contributes 170
commits and the Dez branch contributes 1,026 commits. A read-only merge-tree
simulation at source head `41dabe1755f76059cf7fce321d3e720719678f76`
reported 33 content conflicts. This is too broad for an unverified bulk merge;
the update must move through explicit ownership lanes:

1. **Rendering foundation:** GPUI list scrolling, macOS window material, and
   WGPU changes first, because later chrome and terminal work depend on them.
2. **Native shell:** title bar, recent Workspaces, MultiWorkspace, pane,
   Workspace, Workspaces, persistence, and Workspace Settings together so the
   Workspace → pane → tab hierarchy never exists in two partially merged forms.
3. **Terminal:** PTY metadata, terminal state, terminal element, and terminal
   panel as one lane. Preserve durable Host ownership, access preflight, inline
   launch recovery, provider identity, cmux handoff, and exact root-scoped tmux
   targets while taking upstream renderer and hyperlink fixes.
4. **Tools:** Built-in Agent, Git, extensions, markdown preview, and Settings.
   Retain active-Workspace routing and expose a new preference only after it has
   one native renderer and a deliberate Dez product placement.
5. **Identity and release:** app entry, release channel, manifests, default
   Settings, generated Settings documentation, Dez guards, and fork notes last.
   Product names, bundle identity, release classification, and build policy are
   never accepted as incidental conflict resolutions.

Each lane requires source guards before it lands, then remote compile and
focused tests on the exact intermediate SHA after builds resume. The final
candidate additionally requires optimized packaging and installed-runtime
verification. No lane may use a green later merge to retroactively claim an
earlier intermediate was valid.

### Upstream feature intake

The first upstream candidates are fixes that strengthen existing native owners
rather than add new Dez modes:

- inherit terminal output clipping, sextant glyph rendering, per-line working
  directory hyperlinks, and word-boundary fixes;
- adapt Workspace replacement and selected-Workspace closing to Dez's durable
  MultiWorkspace fallback and Workspaces projection;
- inherit pane retention during save, panel-size reset, zoom-focus stability,
  active-Workspace MCP routing, and the `File` → `Tab` control wording;
- adapt agent-sidebar header alignment and full-screen selected state to the
  shared Dez density, icon, and neutral-selection system; and
- keep advanced agent/model preferences in the native Settings file until a
  user story and renderer justify curated placement.

Broad agent, chat, or sidebar restructuring is deferred when it would create a
second navigation owner. A direct upstream merge remains intentionally paused
until remote build validation is reauthorized.

Synchronization proceeds as a dedicated merge train, not as drive-by copying:

1. Capture exact Dez and upstream SHAs in a clean integration worktree while
   leaving user-owned changes untouched.
2. Inventory upstream changes by native owner: Workspace/panes, project and
   Git, terminal, Agent/ACP, Debug, Settings, GPUI/UI, themes/icons,
   accessibility, packaging, and platform behavior.
3. Classify each change as **inherit**, **adapt**, **defer**, or **reject**.
   Product-policy conflicts are adapted behind existing owners; compatible
   fixes are inherited; no upstream surface is recreated manually.
4. Resolve ownership conflicts before copy conflicts. Dez keeps Home,
   Workspaces, durable terminal ownership, install/access preflight, Lumin,
   curated Settings, and the native-surface rules even when upstream defaults
   differ.
5. Run only source checks until builds resume. Then require focused remote
   regressions and an exact optimized artifact before the merge train becomes
   the new foundation.

The first capability review for `v1.14.2` must explicitly assess Agent command
sandboxing, Project Panel file-operation undo/redo, Agent font roles, Git Panel
access-check performance, large-file input performance, theme/title-bar
matching, terminal TUI rendering, quit/reload fixes, and terminal process-close
semantics. Adoption is conditional on Dez ownership and continuity; a release
note alone is not implementation evidence.

## Settings, design system, and QoL intake

Every curated Settings field must have all six of these before it is exposed:

1. one authoritative settings-store path;
2. one native renderer and keyboard route;
3. one resolved product default;
4. an immediate, observable owner update;
5. accessible name, value, description, focus, and disabled reason;
6. source and exact-artifact evidence for persistence after relaunch.

Rows that are duplicated, diagnostic-only, internal, unsupported, or unable to
meet that contract are removed from the curated pages, not emulated. Advanced
upstream options remain available in the native settings file. Settings pages
follow the product loop: **Workspaces & Terminals**, **Agents**,
**Appearance**, **Workspace & Privacy**, then inherited editor tools.
Current source also removes three product-inert geometry rows from Dez's
curated catalog: outer `card_gap` is intentionally zero, active-pane borders
are intentionally disabled, and `zoomed_padding` has no rendering owner. Their
schema remains available in the native settings file for compatibility.
The native Main Work Area tab strip and adjacent Add control are also fixed
product navigation. Dez omits the inherited tab-bar and tab-button visibility
rows from curated Settings and ignores raw hide or single-tab auto-hide values
for real Main Work Area panes; official Zed retains the upstream controls.

The visual system has one semantic token path for density, typography, corner
style, surface contrast, focus, selection, status, warning, error, success, and
terminal/agent provider identity. Native components consume those roles; a
screen does not invent one-off padding, radii, font sizes, or provider colors.
Icons are semantic reinforcement, never the sole label. The same owner-to-icon
mapping is used in tabs, Workspaces Activity, pickers, Settings, and recovery.

A proposed QoL feature enters v0.5 only when it:

- reduces lost context, attention cost, review risk, session loss, or repeated
  navigation;
- has one existing native owner and a truthful failure path;
- preserves keyboard, screen-reader, narrow-width, reduced-transparency, and
  reduced-motion behavior;
- does not start computation, split panes, grant access, mutate Git, or move
  process ownership without an explicit action;
- has a bounded invalidation and persistence cost; and
- is cheaper to maintain through upstream merges than the user friction it
  removes.

Candidates are prioritized in this order: continuity recovery, navigation
clarity, review safety, terminal-agent handoff, accessibility, performance,
then cosmetic refinement. Features that create another dashboard, history
store, tab model, multiplexer, browser, issue tracker, or settings universe are
out of scope.

## Smoothness and accessibility budgets

- Opening or selecting a Workspace must preserve the current visible owner
  until the requested owner is ready; no blank projection may be introduced by
  a pending asynchronous activation.
- Activity and status updates are event-driven, coalesced, bounded, and silent
  while nothing changes. They do not poll unrelated processes or re-render the
  entire Workspace shell for one metadata update.
- Layout projection scales with visible native panes and tabs. Activity scales
  with bounded actionable work, not historical terminal output or all machine
  processes.
- The Main Work Area remains usable while Git, Search, Debug, terminal-host,
  provider, or multiplexer discovery is slow or failed.
- Every primary journey is keyboard complete, keeps visible focus, announces
  selection/expanded/busy/error state, and preserves the same logical order at
  760x600 through full screen.
- Motion communicates ownership or state change only. Reduced motion removes
  nonessential transitions without hiding progress or focus.
- Lumin Blur and solid fallback themes must preserve text, focus, selection,
  diagnostics, terminal ANSI colors, and status contrast over both bright and
  dark desktop backdrops.

## Surface milestones

### 1. Navigation and chrome

- Keep one native tab strip in every real pane and an adjacent `+` after its
  tabs. Treat that strip as required Main Work Area navigation in Dez rather
  than a user-hideable decoration.
- Make selected tabs, focused panes, title-bar controls, Workspaces rows, and
  the status line follow one density, icon, type, contrast, and radius system.
- Collapse secondary metadata before Workspace, pane, actionable Activity, or
  recovery identity at narrow widths.
- Keep Workspaces optional and restore it from the labeled status-bar action.
- Keep that status-bar action live with `MultiWorkspace`: open or closed state,
  side, active Workspace identity, and attention must never wait for an editor
  or Settings event before its visible and assistive labels update.
- Re-derive the active Activity destination whenever a Workspace header is
  activated or reselected. Returning to the Main Work Area must not erase the
  current terminal or agent projection while waiting for another pane event.
- Remove duplicated navigation, unexplained panes, hover-only actions, and
  product controls that do not map to an existing owner.

### 2. Home and Settings

- Keep Home concise: open or clone a Workspace, start the configured tool,
  resume running work, inspect Files, and review changes.
- Keep Home as the single owner of every empty Dez window, including cold start
  and an explicit no-path new-window or CLI request. Never replace it with an
  inherited onboarding page or an unowned scratch file.
- Use inline installation and access states. Never show a setup tour, mascot,
  centered recovery overlay, or background permission loop.
- Order Settings by the product loop: **Workspaces & Terminals**, **Agents**,
  **Appearance**, **Workspace & Privacy**, then inherited editor tools.
- Give each Dez root Settings page one semantic native icon while keeping the
  full page title; nested section rows remain text-only, and the column width
  follows Interface Density rather than clipping the added hierarchy.
- Require a native renderer and resolved default for every curated field.
  Unsupported structured settings remain available through the native
  settings file instead of a broken control.
- Keep Debugger Settings connected to the existing Debug surface and the active
  Workspace `debug.json`; neither action starts a build.
- Preserve the originating Workspace when Settings is reused. If no Workspace
  owns a Workspace-scoped action, disable it with an explicit explanation
  instead of leaving a visibly enabled no-op.

### 3. Terminal, agents, and multiplexers

- Render Codex, Claude Code, OpenCode, Gemini CLI, Aider, and other TUIs as
  native terminal output with only trusted status and recovery around them.
- Launch Claude Code with `claude`; keep `claude --continue` as a distinct
  resume action.
- Keep tmux as the in-Dez Workspace fallback and external process owner.
- Keep Herdr discovery and attach bounded, retryable, and non-destructive.
- Prefer explicit **Open Workspace in cmux** handoff when cmux is available;
  cmux owns its tabs, panes, browser, hooks, and action registry.
- Preserve legacy sessions by default and describe replacement shells as new
  computation.

### 4. Complete native tool loop

- Prove Files, file tabs, Search, tasks, Diagnostics, Outline, Git Changes,
  Git History, diffs, Review, and Debug through the same pane model.
- Keep loading, empty, denied, stale, disconnected, and failed states compact
  and actionable.
- Keep Debug setup, adapter output, console, breakpoints, Retry, and logs in one
  native Debug lifecycle.
- Turn missing adapters, missing Workspace roots, and adapter boot errors into
  one inline Debug failure with the exact request preserved for Retry. Failed
  preflight must not leave an orphan Debug Session or return silently.
- Preserve ordinary Zed-quality editing, language tooling, keyboard behavior,
  Git, and extension compatibility behind explicit Dez product policy.

### 5. Visual and accessibility system

- Validate Lumin Blur, Lumin, and Lumin Light with normal and reduced system
  transparency.
- Use IBM Plex Sans for interface roles and Lilex for code and terminal roles
  while preserving explicit user font choices.
- Validate Compact, Balanced, and Spacious density across title bar, native
  tabs, Workspaces, Settings, terminal context, notifications, and status.
- Pair every semantic color with text or an icon, expose selected and expanded
  state, preserve visible keyboard focus, and keep screen-reader order aligned
  with the visual hierarchy.
- Validate 760x600, 960x720, 1160x760, 1440x900, and full-screen logical
  viewports without clipping, overlap, horizontal navigation scrolling, or an
  accidental permanent column.

### 6. Continuity and release evidence

- Require stable installation before Workspace restoration or durable-terminal
  startup.
- Preflight each Workspace root once before Git, Search, LSP, agent, or
  terminal work begins.
- Preserve eligible host-owned work through normal quit, relaunch, renderer
  failure, and UI detachment without silent process termination.
- Keep source, remote-CI, installed-runtime, visual, accessibility,
  integration, package, signing, and notarization evidence separate.
- Build and package only through GitHub Actions. Stable promotion requires a
  Developer ID signature, notarization, Gatekeeper acceptance, exact source
  identity, and an Apple M2 artifact audit.

## Stop-ship defects

- startup crash, blank window, re-entrant entity access, quit timeout, or lost
  eligible process;
- invisible Workspaces recovery, missing adjacent `+`, hidden focused pane,
  file replacement, duplicate tab ownership, or unexplained split;
- custom tab chrome, floating onboarding, persistent mascot, task bubble,
  custom permission overlay, fake browser, or permanent inspector;
- dead primary action, inaccessible icon, color-only state, clipped public
  copy, `NO RENDERER`, or `NO DEFAULT`;
- repeated protected-folder prompts, access-error flooding, mismatched terminal
  endpoint, duplicate attach, or destructive legacy recovery;
- false agent lifecycle, transcript-derived success, fake migration, or
  incorrect tmux, Herdr, or cmux ownership;
- source/artifact mismatch, wrong architecture, Preview presented as Stable,
  unsigned Stable package, failed notarization, or failed Gatekeeper check.

## Evidence matrix

| Gate | Required evidence |
| --- | --- |
| Source | exact commit, focused diff, format, identity, theme, and source guards |
| Compiled | exact GitHub Actions run and successful focused regressions |
| Runtime | installed exact artifact, cold start, primary loop, failure paths, quit, and relaunch |
| Visual | exact artifact screenshots for themes, transparency, density, and viewport matrix |
| Accessibility | keyboard, focus, labels, expanded state, contrast, truncation, motion, and screen reader |
| Integration | provider and multiplexer versions, discovery, launch or attach, recovery, and ownership result |
| Package | artifact name, checksum, architecture, bundle identity, signature class, and source SHA |
| Release | Developer ID, notarization, Gatekeeper, tag, rollback point, and known limitations |

## Definition of ready

v0.5 is ready only when the exact installed release candidate proves every
primary story, milestone, stop-ship gate, and evidence row above. Source guards
prove policy only. A plausible screenshot, successful compile, or older green
artifact cannot validate a newer commit.

Until builds resume, source-only polish may advance in small reviewable slices,
but the branch remains an unbuilt v0.5 planning candidate rather than a release.
