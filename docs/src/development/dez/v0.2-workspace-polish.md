# Dez v0.2 Workspace polish

This is the active source-polish lane after the v0.1 hardening baseline. It
does not claim that a v0.2 binary has shipped. [Fork Notes](./fork-notes.md)
remain the permanent product and architecture source of truth.

## Product promise

Dez should feel like one native Workspace, not a terminal dashboard layered
over an editor:

```text
open a Workspace
-> use native tabs for files, terminals, tools, settings, and review
-> reveal Workspaces only when cross-Workspace supervision is useful
-> read current state from the native status bar
```

## Workspace contract

- One Main Work Area owns every ordinary surface through Zed's native tab and
  pane model.
- Files, Git, Debug, and Built-in Agent are destinations in that tab strip,
  not permanent columns.
- Applying a destination layout consolidates existing populated work areas
  into tabs. It never hides or discards their content.
- Split Work Area is the only public workflow that may retain multiple
  populated work areas.
- Workspaces is optional, Workspace-first navigation. It starts closed and uses
  one header, one search affordance, and one options menu. Search becomes
  available when there are multiple Workspaces or sessions to navigate, and
  labels the surface as Workspaces rather than exposing the internal session
  implementation.
- Command Search groups Workspace navigation under **Workspaces** and selected
  session lifecycle actions under **Agent Sessions**. Internal sidebar and
  thread type names do not become product navigation labels.
- Workspace and terminal recovery share one bounded, accessible
  **Workspace notices** region in Workspaces.
- Workspaces status remains Workspace-first when external tmux, Herdr, or cmux
  activity is discovered. Explicit path-matched external activity appends
  secondary context; unrelated machine terminals never enter the navigator.
- Dez does not initialize the legacy machine-wide TTY observer. It therefore
  does not poll `/bin/ps` for a surface the product neither displays nor owns.
- Workspaces search, scope controls, utilities, empty states, and recovery
  actions use the same Workspaces and Workspace vocabulary in visible and
  accessibility labels.
- The bottom native status bar remains visible and owns persistent editor
  state. A terminal context strip appears only for actionable state: an agent
  or task is running, Git changes are ready to review, the terminal has ended
  or failed, or no Workspace is connected.
- The native terminal tab owns the terminal title. Shell-emitted breadcrumbs
  remain available as an opt-in setting, but start off to avoid a duplicate
  title row.
- Dez Settings expose Workspace navigation, terminal, and agent workflows.
  Compatibility controls for removed Session Rail chrome stay out of the
  graphical Settings surface.
- Appearance starts with one scoped **Restore Native Dez Appearance** action.
  Navigation & Layout exposes the native status-bar visibility preference, so
  imported settings cannot leave users without a graphical recovery route.
- MCP and external-agent configuration resolve through the Settings window's
  active Workspace. Retained background Workspaces never receive a hidden
  configuration modal or silently supply the stores shown in Settings.
- First run uses Home and ordinary native tabs. It does not open a mascot,
  overlay, floating coach mark, or duplicate onboarding surface.
- Workspaces does not inject import promotions into ordinary navigation.
  Importing compatible Agent Sessions remains an explicit action in native
  Agent History.
- Help opens that same native Home surface as **Workspace Guide**.

## Acceptance gates

- No startup or restored layout creates an unexplained second pane.
- Back, Forward, Add, Switch Tab, close, drag, split, and status-bar controls
  remain keyboard reachable and use native Zed actions.
- Settings can restore the Dez visual profile without resetting font sizes or
  unrelated preferences, and can show a previously hidden native status bar
  without requiring JSON editing.
- Every native Main Work Area pane keeps an accessible `+` immediately after
  its tabs. The menu opens terminals, files, and Workspace tools through
  existing Zed actions; it does not create a second tab or pane system.
- The left navigator leads with flat native Workspace rows. Each row switches
  the active Workspace, shows live Git branch and changed-file metadata when
  available, and expands only the agent sessions associated with that
  Workspace. It is not a second Files tree or terminal renderer.
- The navigator header exposes one keyboard-accessible `+` that uses Zed's
  same-window **Open Workspace** action. It does not create an empty project
  card or bypass native workspace restoration.
- Opening Workspaces never inserts a promotional banner above or below the
  Workspace list. Agent History retains the discoverable import control.
- Opening or hiding Workspaces does not start a background inventory of
  unrelated applications. Only explicit tmux, Herdr, and cmux integrations use
  their documented discovery interfaces.
- Installing or configuring an MCP extension opens configuration only in the
  active Workspace. Switching Workspaces before opening Settings changes the
  project-scoped MCP and external-agent stores Settings presents.
- A clean active terminal in a connected Workspace has no duplicate metadata
  toolbar above it.
- Workspace destinations preserve all open files, terminals, diffs, and tools
  as tabs when returning to one work area.
- Source identity, product copy, settings grouping, and public documentation
  use Dez and Workspace vocabulary consistently.
- Runtime, visual, accessibility, restart, permission, and packaging evidence
  must come from the exact candidate commit before release.

## Protected folders and release identity

Home reads Recent Workspace names and paths from the Workspace database. It
does not probe those paths on startup. Opening a Workspace is the first action
that may access its files.

macOS still controls `Documents`, `Desktop`, and other protected locations. An
ad-hoc signed development artifact has no stable Apple signing identity, so a
rebuilt artifact can receive a new protected-folder decision even though its
`dev.dez.Dez` bundle identifier is unchanged. A production candidate must use
the Dez Developer ID certificate and notarization inputs already supported by
`script/bundle-mac`. Until those publisher secrets exist, keeping active
codebases under `~/Developer` avoids the Documents prompt; the app must not
pretend an ad-hoc artifact can persist that permission.

## Selective upstream adoption

Dez does not merge upstream `main` wholesale during product-polish work.
Relevant fixes are reviewed against the fork's Workspace and terminal
ownership contracts:

- Zed `23cb8712ba` retains a strong pane entity for the full async save
  operation. Dez adopts this to prevent a suspended save from failing because
  its pane was released.
- Zed `d23aaeebea` calls editor-local lock controls **Tab** controls rather
  than implying they change filesystem permissions.
- Zed `104ccf4bb6` routes shell-driven agent-terminal close requests through
  the navigator's ownership path, so the remaining terminal becomes active
  instead of leaving an uninitialized agent surface.
- Zed `f9a5bf9181` routes extension-provided MCP configuration through the
  active application window and its active Workspace. A retained background
  Workspace can no longer receive an invisible configuration modal.
- Zed `933c85b134` resolves MCP and external-agent stores from the Settings
  window's active Workspace project rather than the first retained Workspace
  or an empty launchpad. Custom-agent setup follows that same active Workspace.

The targeted source patches keep Dez's adjacent tab action, Workspace
navigator, terminal host ownership, and restoration logic intact. They still
require exact-candidate runtime evidence before release.
